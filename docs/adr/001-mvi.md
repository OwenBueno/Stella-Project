# ADR 001: MVI Presentation Pattern

## Status

Accepted

## Context

Stella has high-state enforcement flows (morning lock, task takeover, focus timer) where UI must reflect a single source of truth and respond predictably to user actions and system events (alarms, NFC, sync).

MVVM is simpler but allows ambiguous state when multiple inputs (intents, callbacks, flows) update fields independently.

## Decision

Use **MVI (Model-View-Intent)** for all Android features:

- `UiState` — immutable data class rendered by Compose
- `UiEvent` — sealed interface for user/system actions
- `ViewModel` — reduces events to new state

## Consequences

**Positive**

- Predictable unidirectional flow; easier to test ViewModels
- Enforcement screens can be modeled as explicit states (`Locked`, `AwaitingNfc`, `IntentEntry`)

**Negative**

- More boilerplate than MVVM for simple CRUD screens
- Side effects (navigation, toasts) need explicit channels or callbacks

## Alternatives considered

- **MVVM:** Rejected as primary pattern; allowed only as mental model inside ViewModel
- **MVI hybrid:** Rejected; consistency across features preferred
